Priorities: MUST = operational release/gate; SHOULD = important expansion; COULD = optional enhancement; FUTURE = enterprise. A requirement is PARTIAL until its release-level acceptance is evidenced and PO acceptance is recorded. Test IDs beginning PLAN are prescribed tests not yet implemented; AUTO refers to the existing integration test named in the codebase review.

## Coverage interpretation

Initial customer and POD rows are seeded by setup; no customer/policy administration exists. Job/leg/consignment rows exist, but packages/scans do not. GPS event validation is not continuous tracking. The local prototype's signature/photo controls do not satisfy FR10/12. Existing AUTO tests validate bounded foundation behaviour; planned tests and PO acceptance still determine release completeness.

## Catalogue maintenance

Expand these epics into stories before their sprint. Preserve IDs, source sections, owner, test mapping, dependencies and acceptance evidence. Link changes through `DECISIONS.md` and roadmap backlog. A requirement moving between releases requires an explicit impact-reviewed product decision.
